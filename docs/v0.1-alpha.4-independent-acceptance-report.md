### 4.2 插件文件任务失败

基线运行 `（本机验收 ID 已省略）` 有两次尝试，`toolNames` 都是空数组。回答出现原始 DSML 工具调用文本，但没有工具事件，也没有预期文件。

这两种证据需要一起看：**模型已经可用，普通 DSH 能执行工具；插件 Agent 没有发生真实工具调用。** 尚不能排除修好工具组合后出现进一步的工作区权限问题，所以恢复文件能力后必须再次做真实写入读回验收。

### 4.3 为什么“模型能回复”还不等于“Agent 能执行文件任务”

Agent 需要模型、工具注册、权限、工作区和会话生命周期共同组成。把“请使用文件工具”写进提示词不会自动注册工具。

插件在 [agent-runner.ts:50](（本机路径已省略）) 调用 `ctx.agents.create`，只传了会话、cwd、模型和 signal，没有 setup。当前安装的 DSH 普通会话则先 `composeAgent(presetId)`，再给 `agents.create` 传 `setup: composition.setup`。

**这是已确认的实现差异，也与本轮现象吻合，是 WF-A4-001 最应先验证的根因。** 修复应使用当前 DSH 正式支持的 Agent preset 挂载路径，同时保留既有文件策略和审批规则；不能靠解析模型回复中的 DSML 去代替正规工具调用。

## 5. 六项问题的复现和定位

### WF-A4-001：插件 Agent 缺少真实工具能力

复现：配置模型 → 打开“Codex 亲测 Alpha.4 节点与执行”或“AI 三步流程” → 运行 → 查看结果和实际文件。基线重试也未成功。

预期：DSH 工具事件包含文件读写，输出文件存在、内容可重新读取。  
实际：`toolNames=[]`，回复出现 DSML，预期文件不存在。

定位：`src/host/agent-runner.ts:50`；对照当前安装的 `@deepseek-ai/dsh-api-session-controller/lib/index.js:449` 及 `:457`。

### WF-A4-002：切换生成结果后残留旧运行

复现：打开已有失败运行的手动流程 → AI 生成新流程 → 保存新流程。新流程还没有运行，却显示旧流程的尝试、`dsh-preparation-check.md` 错误和重试按钮。Markdown 导入也出现同样情况。

定位：[client/index.tsx:300](（本机路径已省略）) 的 `generatePlan` 和 `:321` 的 `importMarkdown` 没有清理 `run`；`selectSaved` 和 `createNew` 有清理。应在工作流身份变化时清理旧运行及预览，并在显示/操作时核对 `run.workflowId`。

证据：`evidence/ai-draft-after-save.txt`、`screenshots/ai-draft-stale-run-history.jpg`。

### WF-A4-003：第二个宿主错误恢复第一个宿主的活运行

复现：3085 运行三步文本流程，第一步等待人工验收；保持其进程 37016 和运行锁存活；启动相同 DSH_HOME 的 3086 宿主。

实际：运行 `（本机验收 ID 已省略）` 被 3086 启动恢复逻辑改为 interrupted，理由是“DSH Host 在运行期间关闭”。但 3085 仍存活，3086 再点击运行还明确拒绝并提示进程 37016 持有本地锁。人工通过被拒绝。

停止本轮新增宿主并用单入口重启后，尝试数和结果仍保存，但该 interrupted 任务仍显示通过/驳回按钮；点击通过提示“只有正在等待人工验收的任务可以通过”。它也没有可用的同任务重试入口。

定位：[storage.ts:244](（本机路径已省略）) 对全部活动状态直接恢复，未核对活运行锁所有者。`acquireLock` 在 `:307` 已有进程存活检查，但恢复没有复用。恢复仅应处理确认失去宿主的运行；中断的 needs_review 任务也需要明确的可恢复状态和可用操作。

证据：`multi-host-interrupted-run.json`、`multi-host-ui.txt`、`interrupted-review-after-restart.txt`。

### WF-A4-004：继续动作丢失唤醒且返回旧状态

复现：暂停控制流程第一步运行时点击暂停 → 第一项完成后停在边界 → 点击继续。

运行 `（本机验收 ID 已省略）` 已写入 run.resumed，state=running，但 58.3 秒后第二、三项尝试数仍为 0。页面继续显示 paused 和“继续”。

定位：[host/index.ts:277](（本机路径已省略）) 先唤醒 Promise 再异步更新 state。等待循环 `:578` 被唤醒时可能重新读到 paused，重新进入等待；随后 state 虽更新，新的等待器不会被唤醒。resume 分支也没有重新获取 run，方法返回旧的 paused 对象；Client 对 paused 不轮询，导致页面也停住。

修复方向：先完成状态持久化，再唤醒等待器，返回最新记录；明确处理并发的 resume/cancel。该原因由本地源码和状态证据推断，尚未进行修改后验证。

证据：`resume-stalled-run.json`、`resume-stalled-ui.txt`、`screenshots/resume-stalled.jpg`。

### WF-A4-005：暂停阶段取消被写成失败

复现：上述边界等待/继续卡住时点击停止。实际控制器结束，运行锁释放，但 state=failed，事件为 run.failed，错误为“操作已取消。”。

定位：`waitAtPauseBoundary` 遇 abort 会抛 AbortError；外层 executeRun 的 catch 经 `finishUnexpected` 写为失败，越过正常的 cancelled 收尾。应统一取消异常的归类及资源清理，并验证活动 Agent、暂停边界、人工等待三个阶段。

本轮活动 Agent 期间停止确实得到 cancelled；因此不能把所有停止操作归为通过。

### WF-A4-006：AI 草稿资料节点遮挡任务

复现：在已有 File/Prompt 的手动流程上生成三步草稿 → 保存 → 重载打开并 Fit View。

1600×1000 实际画布中，task-2 的矩形约为 `(786.44,542.05,177.91,125.39)`；参考文件节点约为 `(793.98,575.97,177.91,93.48)`，两者明显重叠。资料节点盖住任务卡片的大部分内容。不是重载导致节点丢失：DOM 中仍有 5 个节点。

原因方向：生成任务使用固定新位置，已有上下文节点保留旧位置，两组布局没有避让。应在生成草稿时为任务和资料安排不重叠的位置，并保留用户手工拖动的可编辑性。

证据：`evidence/ai-node-overlap.json`、`screenshots/final-file-execution-failed.jpg`。
